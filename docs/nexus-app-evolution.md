# Nexus Studio 앱 진화 원칙

이 문서는 Nexus Studio 앱 포트폴리오를 장기적으로 점검하고 개선하기 위한 기준점이다. 자동 점검은 이 문서를 읽고, 최신 코드와 실제 증거를 기준으로 내용을 갱신한다.

## 목표

- 프로모션, 브랜드 사이트, 웹사이트 제작을 하나의 재사용 가능한 자동화 흐름으로 연결한다.
- 내부 구조는 사람의 클릭 동선보다 AI가 안정적으로 탐색·조합·실행하기 쉬운 계약을 우선한다.
- 사람용 화면은 Apple의 제품 원칙에서 배울 수 있는 명료함, 점진적 공개, 일관된 피드백, 절제된 시각 위계를 지향한다.
- 앱 수를 늘리는 것보다 실제 작업 성공률과 재사용률을 높인다.

## 2026-08-29 기준선

- 앱 레지스트리: 33개
- 베타: 11개
- 비활성: 4개
- 관리자 전용: 19개
- `visual-flux`: 레지스트리에는 있으나 구현 디렉터리가 없는 준비 상태
- 앱별 UI와 Firebase/Gemini 연결은 넓게 분산되어 있지만, `src/server/nexus/adapters`의 헤드리스 실행 어댑터는 일부 핵심 엔진에 집중되어 있다.
- 루트 스크립트에는 전체 빌드·린트와 MCP 스모크 테스트가 있으나 앱별 계약 테스트를 실행하는 공통 테스트 명령은 없다.

## 현재 우선 문제

1. **포트폴리오 과밀** — 비슷한 역할의 앱과 버전이 병존해 핵심 흐름과 실험 기능의 경계가 흐리다.
2. **AI 실행 계약 부족** — `canReceive`/`canSend`는 화면 연결 힌트에 가깝고, 입력 스키마·출력 스키마·오류·부작용·멱등성까지 표현하는 공통 계약이 아니다.
3. **프로모션 흐름 단절** — Brief, Archive, Codex, Preview, Skin, Theme, Review 사이에 공유하는 캠페인 객체와 실행 상태 모델이 없다.
4. **검증 편차** — 앱별 테스트와 성공 기준이 통일되지 않아 UI에서 되는 것과 자동 실행에서 되는 것이 다를 수 있다.
5. **대형 컴포넌트와 중복** — 일부 앱은 단일 `index.jsx`에 상태·데이터·UI가 결합되어 있고, 버전별 구현이 공통 계약 없이 갈라져 있다.
6. **UI 일관성 편차** — 전역 테마 토큰은 있으나 앱별 인라인 스타일과 상호작용 규칙이 많아 정보 위계, 빈 상태, 진행 상태, 오류 복구 방식이 달라진다.

## 주간 평가 점수

각 앱을 100점 기준으로 평가하되, 코드 줄 수나 기능 수보다 작업 성공 증거를 우선한다.

| 항목 | 배점 | 확인 내용 |
| --- | ---: | --- |
| 실제 효용 | 30 | 반복 사용 가능성, 산출물 품질, 수동 단계 절감, 다른 앱의 소비 여부 |
| AI 사용성 | 30 | 발견 가능성, 구조화 입력/출력, 조합성, 멱등성, 안정적 식별자, 명시적 오류 |
| 신뢰성 | 20 | 테스트, 관측 가능성, 실패 복구, 데이터 안전, 성능 |
| 사람용 UX | 10 | 명료성, 점진적 공개, 접근성, 상태 피드백, 시각 일관성 |
| 전략 적합성 | 10 | 프로모션·브랜드 사이트·웹 자동화 핵심 흐름과의 연결성 |

## AI 우선 앱 계약

장기적으로 모든 핵심 앱은 UI와 분리된 다음 계약을 제공해야 한다.

- 안정적인 `appId`, `operationId`, 버전
- 기계가 읽을 수 있는 입력·출력 스키마
- 읽기/쓰기/외부 호출 등 부작용 선언
- 멱등성 키와 재시도 정책
- 진행 이벤트와 구조화된 오류 코드
- 결과물, 근거, 품질 점수, 다음 실행 후보를 담는 공통 실행 결과
- UI 없이 실행 가능한 헤드리스 함수와 최소 계약 테스트

`src/config/apps.js`는 표시용 레지스트리에서 시작해 이 계약의 발견 인덱스로 발전시킨다. UI는 동일 계약을 소비하는 하나의 클라이언트로 취급한다.

## 사람용 UI 원칙

- 한 화면에는 한 가지 주된 작업과 한 가지 주 버튼만 선명하게 둔다.
- 고급 설정은 기본 화면에서 숨기되 현재 적용값과 되돌리기 경로는 항상 보이게 한다.
- 생성·업로드·평가·발행 상태는 동일한 언어와 컴포넌트로 표현한다.
- 애니메이션은 상태 변화 설명에만 사용하고 `prefers-reduced-motion`을 존중한다.
- 색상, 간격, 모서리, 타이포, 포커스, 빈 상태, 오류 상태를 공통 토큰과 프리미티브로 통합한다.
- Apple의 외형을 복제하기보다 복잡성을 숨기는 정보 구조와 정교한 피드백 원칙을 적용한다.

## 포트폴리오 결정 규칙

- **Core**: 반복 성공 증거가 있고 핵심 자동화 흐름에서 소비된다.
- **Improve**: 전략적 가치가 있으나 계약·품질·UX 보완이 필요하다.
- **Merge**: 다른 앱과 역할이 겹치며 독립 앱보다 공통 모듈이나 모드가 낫다.
- **Experiment**: 가설과 성공 기준, 종료 시점이 명확한 베타다.
- **Retire**: 대체 경로가 있고 유지 비용이 효용보다 크다.

새 앱은 기존 앱 두 개 이상에서 반복되는 능력 공백이 확인되고, 공통 모듈이나 기존 앱 확장으로 해결할 수 없을 때만 만든다. 처음부터 완성형 UI를 만들지 않고, 스키마·헤드리스 실행·계약 테스트·최소 UI 순서로 작은 수직 슬라이스를 제작한다.

## 반복 개선 절차

1. 레지스트리, 최근 변경, 오류 흔적, 테스트 결과, 사용 가능한 실행 기록을 수집한다.
2. 매주 핵심 흐름 하나와 회전 대상 앱 3~5개를 평가한다.
3. 가장 큰 문제를 재현하고 점수와 근거를 기록한다.
4. 위험이 낮고 검증 가능한 개선 한 건 이상을 직접 구현한다.
5. 빌드·린트·관련 테스트로 검증한다.
6. 큰 구조 변경이나 새 앱은 먼저 계약과 수직 슬라이스를 제안하고, 타당성이 충분하면 같은 주기 안에서 구현을 시작한다.
7. 변경 내용, 점수 변화, 남은 위험, 다음 주 대상을 이 문서의 실행 기록 또는 별도 주간 보고서에 남긴다.

## 첫 번째 권장 축

가장 먼저 `BriefStudio → BannerCodex/PromotionArchive → NexusPreview/PromoSkin → BrandWebReview`를 하나의 Campaign 계약으로 연결한다. 동시에 `src/server/nexus`의 어댑터 패턴을 앱 공통 실행 계약으로 확장하고, 사람용 화면은 공통 상태·설정·결과 프리미티브를 소비하도록 정리한다.
